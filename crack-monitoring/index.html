Lens-distortion correction

Calibrate once. Reuse the correction.

OpenCV estimates the lens parameters offline. The application then loads those saved parameters and prepares reusable correction maps at runtime.

01 / Offline camera calibration

Estimate the camera parameters.

Checkerboard images captured at varied positions and orientations are processed with OpenCV. findChessboardCorners locates the pattern, cornerSubPix refines the image coordinates, and calibrateCamera estimates the camera matrix and distortion coefficients. The results are stored in camera_params.npz.

Checkerboard views→findChessboardCorners→cornerSubPix→calibrateCamera→camera_params.npz

02 / Runtime lens correction

Prepare the mapping once per run.

The CameraWorker loads the saved matrix and coefficients. Once the first frame establishes the stream resolution, initUndistortRectifyMap generates resolution-specific lookup maps. remap then reuses those maps to correct each incoming frame.

Load parameters→First-frame resolution→initUndistortRectifyMap→remap every frame

Physical-scale initialization

A separate step converts pixels into physical units.

After lens correction, the system detects the checkerboard in the operating view. The known square size and measured pixel span establish the mm/px scale used by the measurement pipeline.

Scale can be initialized at startup, updated manually, and refreshed during event recording. If an update fails, the most recent valid scale remains available.

Known distance (mm)/Measured span (px)= scale (mm/px)

Segmentation and measurement

From a pixel-level boundary to physical crack dimensions.

The same corrected frame and established physical scale support instance-level identification, length estimation, and maximum-width estimation.

Event state and rolling buffer

The event record includes what happened before the trigger.

A local TCP socket connects the host seismic system to the monitoring application. Start and stop signals carry the same event ID through the controller to every active camera worker.

TCP socket interface

Two messages coordinate one event ID.

Event start event_occurred=1,no={event_id} Application response: ACK_START
Event stop event_occurred=0,no={event_id} Application response: ACK_STOP

System response

Parse once. Broadcast to every active camera.

  1. 01

    The socket server parses event_occurred and no, then acknowledges the host system.

  2. 02

    MainController forwards the event ID and state to all active CameraWorkers.

  3. 03

    Each DataManager manages its own buffer, phase state, image files, and CSV record inside the shared event archive.

Archive and traceability

Images and measurements remain linked by event, camera, and time.

Each event contains a separate directory for every active camera. The measurement log points back to the raw and annotated images from the same timestamp and records whether each packet belongs to the pre-event, during-event, or post-event phase.

Application and delivery

The pipeline was delivered as one operational application.

The final system was packaged for direct operational use rather than delivered as source code that required a developer-managed environment.

Self-contained Windows application

Launch the system without assembling a Python environment.

The application was packaged with PyInstaller as a windowed executable, bundling the program and its runtime dependencies. Operators can launch the monitoring system directly without installing Python, creating a virtual environment, or running source files from a command line.

Camera sources, model and calibration paths, processing settings, socket port, and archive location remain editable through the external config.json, so deployment settings can change without modifying the application code.
